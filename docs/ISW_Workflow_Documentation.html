2. Workflow Utama (Master Workflow)

Platform ISW terdiri daripada 17 modul yang saling berkait berdasarkan perjalanan rawatan pesakit, dari hubungan pertama (lead) melalui onboarding, rawatan aktif, sehingga graduasi ke Geng ALIVE.

Peta Modul Peringkat Tinggi

PESAKIT BAHARU │ ▼ [1] KYC & Pendaftaran ──────────────► [2] KOB (Konsultasi Overhaul Body) │ │ │ ▼ │ [3] Pemilihan Pakej Rawatan & Pembayaran │ │ │ ▼ │ [4] Tandatangan Kontrak Digital │ │ ▼ ▼ [5] Dashboard Pesakit ◄──────────────► [6] Timeline Rawatan (auto-generate) │ ▲ │ │ │ ▼ ▼ │ [7] Slot Klinik (booking) [8] Check-in Harian ─────► [9] Dashboard Kepatuhan ◄─── [10] Dashboard Coach │ ▲ │ ▼ │ ▼ [11] Vitals (BP, HbA1c) [12] Alert Kepatuhan ─────► [13] Plan-Week Entry │ │ │ ▼ [14] Akses Library ◄─── (filter package_ids) [15] Tanda Hadir │ │ ▼ ▼ [16] Pulangan Botol [17] Auto-Tolak Inventori │ │ │ ▼ │ [Audit Log] ▼ ▲ [Perkhidmatan Pesakit: Orders, Issue, Surat, Pembayaran]───────────┘ │ ▼ [Dashboard Governance] │ ▼ [Status Outcome] │ ▼ [Geng ALIVE — Fasa 3]

Pemicu & Peralihan Antara Modul

  1. Lead → KYC: Closer/admin cipta pesakit baru ATAU pesakit daftar sendiri. Hantaran borang trigger sync GHL Fasa 3.
  2. KYC → KOB: Bila KYC selesai, pesakit dialih ke booking KOB. Pembayaran sahkan booking.
  3. KOB → Pakej: Selepas cadangan doktor semasa KOB, pesakit browse pakej dan bayar.
  4. Pakej → Kontrak: Pembayaran berjaya → template kontrak auto-load; pesakit mesti tandatangan sebelum rawatan.
  5. Kontrak → Timeline: Kontrak ditandatangan → auto-generate jadual per-minggu dari coaching_schedule JSONB dan cipta baris sesi.
  6. Timeline → Check-in Harian: Pesakit terima notifikasi pada setiap aktiviti dijadual (madu, zikir, dll.) dan log kepatuhan.
  7. Check-in → Alert Kepatuhan: Kepatuhan rendah (< 5 madu/hari untuk 4-5 hari) auto-trigger alert coach.
  8. Tanda Hadir → Tolak Inventori: Sesi F2F ditanda hadir → psy_inventory_items.qty_in_stock auto-tolak ikut bekalan minggu tu.
  9. Threshold Inventori → Auto-Beli Fasa 2: Stok ≤ 30% trigger jana invois pembelian.
  10. Tamat Rawatan → Outcome: Coach kemaskini outcome_status (Berhenti / OTW / Meninggal). Pesakit graduate ke Geng ALIVE Fasa 3.
Ringkasan: Workflow utama berpusat pada kitaran rawatan. KYC → KOB → Pakej → Kontrak → Timeline → Aktiviti harian → Outcome. Setiap modul masuk ke Dashboard Governance dan Audit Log untuk akauntabiliti. Inventori, Pembayaran, dan Notifikasi adalah perkhidmatan rentas modul.

3. Sub-Workflow 1: KYC & Pendaftaran

Pengguna Utama: Admin Closer Pesakit (daftar sendiri)

Langkah

  1. Pemicu: Pesakit baru masuk sistem (Admin masukkan manual, webhook GHL Fasa 3, atau pesakit daftar sendiri).
  2. Pesakit/Staf hantar borang KYC mengandungi IC, Nama Penuh, Telefon, Alamat, Waris Kecemasan, Keadaan Kesihatan. Popup pengesahan: "Maklumat ini adalah maklumat PESAKIT, bukan pewaris".
  3. Titik Keputusan: Pengesahan
    • Diluluskan → pesakit diaktifkan, psy_patients.status = 'active'
    • Pending → admin semak hantaran
    • Ditolak → pesakit dimaklumkan dengan sebab; boleh hantar semula
  4. Auto-tuntut rekod sedia ada: Jika pesakit daftar dengan IC yang sama dengan rekod unregistered yang dicipta staf, sistem link kedua-duanya.
  5. Trigger modul seterusnya: KYC diluluskan → pesakit dialih ke booking KOB.

Titik Keputusan & Pengendalian Ralat

  • IC duplikat → block hantaran dengan mesej ralat
  • Field wajib tak diisi → validasi borang block submit
  • Staf cipta manual → tiada popup KYC perlu (staf isi semua field)
  • Sync GHL gagal Fasa 3 → fallback manual entry; queue retry
Ringkasan: KYC adalah pintu masuk. Ia kumpul maklumat pesakit wajib, validate identiti, dan sahkan data adalah pesakit (bukan waris). Selepas diluluskan, pesakit ke KOB.

4. Sub-Workflow 2: KOB (Konsultasi Overhaul Body)

Pengguna Utama: Closer Doktor Pesakit

Langkah

  1. Pemicu: KYC diluluskan → pesakit nampak CTA "Tempah KOB" di dashboard.
  2. Pesakit browse slot KOB yang tersedia dari psy_kob_slot_config (ditapis ikut cuti klinik).
  3. Pesakit pilih slot + buat pembayaran (FPX/Kad/Transfer/GHL).
  4. Pembayaran berjaya → kob_status = 'paid', pesakit terima video selamat datang + Lokasi ISW + pengesahan WhatsApp Fasa 3.
  5. Pada hari KOB: Doktor tanda pesakit hadir. Nota cadangan disimpan.
  6. Titik Keputusan:
    • Pakej disyorkan → pesakit ke pemilihan Pakej
    • Tiada pakej → closer key-in cadangan untuk masa depan
  7. Aliran status: na → pending_payment → paid → kyc_done → booked → hadir → package_recommended → completed

Titik Keputusan & Pengendalian Ralat

  • Pesakit tidak hadir → tanda tidak_hadir; auto-caj jika berkenaan
  • Reschedule → pertama percuma; reschedule seterusnya caj RM50 (masa depan)
  • Slot penuh → validasi real-time elak booking berganda
  • Pembayaran gagal → kekal pending_payment; peringatan 24 jam
Ringkasan: KOB adalah konsultasi diagnostik. Pesakit bayar, hadir, dan terima cadangan rawatan. Aliran status mengunci modul seterusnya sehingga selesai.

5. Sub-Workflow 3: Pakej Rawatan

Pengguna Utama: Admin Pesakit

Langkah

  1. Pemicu: KOB selesai → pesakit nampak pakej disyorkan dalam pakej.html.
  2. Pesakit browse dengan penapis (Kategori, Tempoh, Harga).
  3. Pesakit klik Detail → lihat dalam pakej-detail.html:
    • Ringkasan Pakej (harga, tempoh, sesi)
    • Bekalan & Inventori (bekalan diterima)
    • Timeline Rawatan (milestone visual)
    • Jadual Harian (template aktiviti harian)
    • Kontrak Pakej (8 klausa dengan interpolasi variable)
    • Kandungan Pakej (library content yang dikait)
  4. Pesakit bayar melalui payment.html.
  5. Pembayaran berjaya trigger:
    • active_package_id set pada pesakit
    • Auto-cipta psy_treatment_plans dengan coaching_schedule disalin
    • Auto-generate sesi per-minggu dalam psy_plan_weekly_progress
    • Buka aliran tandatangan Kontrak
  6. Admin urus pakej dalam pakej-edit.html: Cipta/edit maklumat asas, bekalan, timeline, jadual harian, klausa kontrak. Mode Draft sembunyi dari katalog; Aktif publish.

Titik Keputusan & Pengendalian Ralat

  • Pesakit tukar fikiran → cart dikosongkan, tiada caj
  • Pakej percuma (RM0) → skip gateway pembayaran; auto-aktif
  • Pembayaran timeout → status pending_payment; auto-batal selepas 48 jam
  • Stok tak cukup Fasa 2 → block pembelian
Ringkasan: Pesakit pilih dan beli pakej rawatan. Setiap pakej bawa spesifikasi rawatan penuh (timeline, bekalan, kontrak, akses kandungan). Admin urus pakej dengan workflow draft/aktif.

6. Sub-Workflow 4: Kontrak Digital & Onboarding

Pengguna Utama: Pesakit Admin

Langkah

  1. Pemicu: Pembayaran pakej berjaya → modal kontrak terbuka.
  2. Sistem load template dengan interpolasi variable: {{patient_name}}, {{patient_ic}}, {{package_name}}, {{price}}, {{today}}.
  3. Pesakit baca 8 klausa: Pengenalan, Komitmen Pesakit, Konfidensial, Reaksi Pemulihan, Bayaran, Ketidakhadiran, Pengakhiran, Pengesahan.
  4. Pesakit tandatangan secara digital (pad e-signature).
  5. Sistem simpan PDF yang ditandatangan; timestamp agreement_signed_at di-set.
  6. Bahan onboarding dihantar: Video selamat datang, Video Lokasi ISW, Akses Library dibuka, Peringatan sesi pertama dijadual.

Titik Keputusan & Pengendalian Ralat

  • Pesakit tolak tandatangan → rawatan diblok; closer follow-up
  • Tandatangan semula untuk upgrade → kontrak baharu dengan terma kemaskini
  • Upload storan gagal → queue retry; admin dimaklumkan
Ringkasan: Sebelum rawatan bermula, pesakit mesti tandatangan kontrak digital. Sistem simpan dokumen ditandatangan dengan timestamp untuk pematuhan undang-undang.

7. Sub-Workflow 5: Timeline Rawatan & Sesi

Pengguna Utama: Coach Doktor Admin Pesakit (lihat)

Langkah

  1. Pemicu: Pembayaran pakej → coaching_schedule disalin ke psy_treatment_plans.
  2. Sistem auto-generate baris sesi dalam psy_plan_weekly_progress (satu per minggu, status booked).
  3. Setiap objek minggu mengandungi: Minggu #, Mode (F2F/Online/Both), Item Bimbingan, Item Aktiviti, Bekalan dengan kuantiti.
  4. Pesakit nampak timeline dalam plan.html: Bar milestone visual, detail per-minggu, peringatan sesi seterusnya.
  5. Coach/Doktor edit per-minggu dalam plan-week.html: Kemaskini bimbingan/aktiviti/bekalan; tanda hadir/tidak_hadir/cancel/reschedule.
  6. Aliran Tanda Hadir:
    • Status → hadir
    • Jika mode F2F → deductSessionSupplies() jalan → inventori auto-tolak
    • Audit log: inventory.auto_deducted
    • Banner: "📦 Bekalan ditolak: IB −1kg, Madu −2botol"
  7. Aliran Reschedule:
    • Sesi asal → cancel
    • 2 sesi baru dicipta di hujung dengan status extension_pending_payment
    • Pesakit dimaklumkan: "Bayar RM50 untuk lanjutkan ke Minggu N"
    • Pembayaran berjaya → extension → booked

Titik Keputusan & Pengendalian Ralat

  • Mode online → tiada tolak inventori (tiada bekalan fizikal)
  • Sesi extension (is_extension = true) → skip tolak (sudah dikira dalam asal)
  • Pesakit tanda hadir sendiri → diblok; hanya coach/doktor/admin
  • Item tak jumpa dalam inventori → log ralat, skip, sambung yang lain
  • Stok tak cukup → set qty kepada 0 (tiada negatif); amaran kepada coach
Ringkasan: Setiap pakej automatik generate timeline rawatan per-minggu. Coach urus kehadiran dan detail per-minggu. Kehadiran F2F trigger auto-tolak inventori dengan jejak audit penuh.

8. Sub-Workflow 6: Check-in Harian & Kepatuhan

Pengguna Utama: Pesakit Coach

Langkah

  1. Pemicu: Setiap hari, pesakit buka checkin.html (atau terima notifikasi dijadual).
  2. Pesakit log:
    • Bilangan madu (target dari pkg.madu_frequency_per_day)
    • Skor mood (1-10)
    • Skor tenaga (1-10)
    • Aktiviti selesai (pilih banyak)
    • Simptom / reaksi pemulihan
  3. Sistem simpan ke psy_daily_checkins dengan cap tarikh.
  4. Auto-ringkasan dalam kepatuhan.html:
    • Paparan pesakit: Chart madu 14 hari, trend mood, streak, kehadiran sesi
    • Paparan staf: Semua pesakit dengan % kepatuhan, sorotan kepatuhan rendah
  5. Auto-trigger Alert Kepatuhan: Bilangan madu < target untuk 4-5 hari/minggu → coach assigned terima alert; muncul dalam dashboard coach hujung hari.
  6. Coach akui alert: Semak sejarah, hubungi pesakit via WhatsApp/call, tanda acknowledged.

Titik Keputusan & Pengendalian Ralat

  • Simptom kritikal Fasa 2 → auto-tunjuk solusi + butang "Call Coach"
  • Madu < 5/hari untuk 4-5 hari → pesakit tak boleh hadir sesi; disclaimer ditunjukkan
  • Terlepas check-in → peringatan esok; streak terputus
  • Entry lewat (selepas tengah malam) → dikira untuk hari sebelum hanya jika dalam 6 jam
Ringkasan: Check-in harian adalah mekanisme kepatuhan utama. Pesakit log madu, mood, dan aktiviti; sistem auto-ringkas untuk pesakit dan coach. Kepatuhan rendah trigger alert coach automatik.

9. Sub-Workflow 7: Pengurusan Inventori

Pengguna Utama: Admin Manager Coach (lihat)

Langkah

  1. Admin urus inventori dalam inventory.html:
    • Tambah/edit item (nama, kategori, unit, min_qty, qty_in_stock)
    • Set consumption_type: fixed (manual) atau package (auto-derived dari pesakit aktif)
    • Item pakej: dynamic_monthly = (pesakit aktif) × (penggunaan per-pesakit)
  2. Auto-tolak pada kehadiran F2F (lihat Sub-Workflow 5).
  3. Pengesanan stok rendah:
    • Item fixed: qty_in_stock ≤ min_qty → tanda rendah
    • Item pakej: qty_in_stock ≤ 30% × dynamic_monthly → tanda rendah
  4. Trigger auto-beli Fasa 2: psy_inventory_requests status pending_approval → kewangan lulus → pembelian.
  5. Penambahan manual: Admin tambah stok via "Terima Stok"; entry audit log dicipta.

Titik Keputusan & Pengendalian Ralat

  • Item perlu kelulusan (requires_approval = true) → aliran manual walaupun item pakej
  • Sesi F2F dibatalkan sebelum hadir → tiada tolak
  • Cubaan stok negatif → had pada 0; alert admin
  • Item dipadam dengan rujukan aktif → soft-delete sahaja (simpanan audit)
Ringkasan: Inventori jejak semua bekalan klinik dengan auto-tolak pada kehadiran F2F. Threshold stok trigger permohonan pembelian (Fasa 2). Admin ada kawalan penuh; coach lihat sahaja.

10. Sub-Workflow 8: Slot Klinik

Pengguna Utama: Admin Pesakit Coach

Langkah

  1. Admin konfigurasi slot dalam halaman Slot Klinik:
    • Dua kategori: Slot KOB dan Slot Rawatan
    • Per slot: julat masa (cth "9.30 - 11.30 pg"), tempoh auto-kira
    • Per hari (Rabu-Ahad): toggle ON/OFF
  2. Admin urus cuti dalam closures.html: Auto-seed Aidilfitri, Aidiladha, Deepavali (berulang) + tarikh custom.
  3. Override Per-Tarikh oleh Admin: Tarikh tertentu override default. Cth: "Jumaat 15 Mei: hanya slot 2.30ptg".
  4. Pesakit tempah slot: Picker slot tunjuk ON + tarikh bukan-cuti. Slot direzab 5 minit pada pemilihan.
  5. Pesakit bayar → booking disahkan; bilangan slot dikurangkan untuk tarikh tu.

Titik Keputusan & Pengendalian Ralat

  • Lock mode per pakej: Minggu pakej online → hanya slot Online; f2f → hanya F2F
  • Slot penuh → tarikh seterusnya ditunjukkan
  • Cuti pada tarikh dipilih → block pemilihan; label cuti ditunjukkan
  • Race condition (booking serentak) → commit pertama menang; kedua nampak "slot diambil"
  • Admin tanda slot OFF selepas booking → booking sedia ada dihormati; baharu diblok
Ringkasan: Slot Klinik adalah lapisan penjadualan operasi. Admin tetapkan slot tersedia per hari; cuti klinik auto-lock tarikh. Pesakit tempah slot yang padan dengan kekangan mode pakej.

11. Sub-Workflow 9: Dashboard Coach & Patient Hub

Pengguna Utama: Coach Doktor Admin

Langkah

  1. Coach log masuk → nampak dashboard: Senarai pesakit assigned (atau SEMUA jika dinaik taraf), Sesi hari ini, Alert kepatuhan terbuka, Pesakit kepatuhan rendah disorot.
  2. Coach buka Patient Hub (patient-hub.html): Profil, pakej, minggu semasa, vitals, check-in terakhir. Tab: Sesi, Check-in Harian, Vitals, Akses Library, Kepatuhan, Audit.
  3. Tindakan Coach:
    • Tanda sesi hadir / tidak_hadir / reschedule
    • Kemaskini nota rawatan per-minggu
    • Tambah nota coaching (teks atau rakaman suara Fasa 3)
    • Hantar notifikasi pesakit
    • Akui alert kepatuhan
  4. Coach kemaskini status outcome apabila rawatan tamat: OTW / berhenti / meninggal → kemaskini dashboard governance.

Titik Keputusan & Pengendalian Ralat

  • Pesakit ditandakan kritikal Fasa 2 → banner Red Flag Escalation; setup lawatan ward
  • Coach tak assigned ke pesakit → read-only (Fasa 3: semua coach akses penuh)
  • Edit serentak → last-write-wins dengan amaran versi
  • Simpan nota gagal → draft disimpan di localStorage
Ringkasan: Coach pantau dan urus kohort pesakit mereka. Patient Hub bagi paparan 360° setiap pesakit. Tindakan coach feed balik ke jejakan kepatuhan dan laporan outcome.

12. Sub-Workflow 10: Notifikasi & Komunikasi

Pengguna Utama: Semua pengguna (penerima)

Langkah

  1. Acara sistem trigger notifikasi:
    • Hantaran KYC baharu → admin
    • Alert kepatuhan → coach
    • Peringatan sesi → pesakit (24 jam, 1 jam sebelum)
    • Pembayaran berjaya → pesakit
    • Inventori rendah → admin/manager
    • Isu dihantar → admin
  2. Penghantaran dalam aplikasi: jadual psy_notifications; ikon loceng tunjuk bilangan tak dibaca; klik untuk tanda dibaca.
  3. Penghantaran WhatsApp/Email Fasa 3: Bridge ke API WhatsApp Business (WATI/360dialog); template per acara; throttling + retry.
  4. Alert kritikal: Pesakit Red Flag → notifikasi segera kepada SEMUA coach + admin. Stok inventori habis → rantaian perolehan.

Titik Keputusan & Pengendalian Ralat

  • Pilihan notifikasi pengguna → email vs WhatsApp vs kedua-dua
  • Waktu senyap Fasa 3 → notifikasi bukan-kritikal dikumpul
  • Penghantaran WhatsApp gagal → fallback SMS Fasa 3
  • Email bounce → tanda dalam profil pengguna
Ringkasan: Semua acara sistem melalui hab notifikasi pusat. Penghantaran dalam aplikasi berfungsi hari ini; integrasi WhatsApp/Email datang Fasa 3.

13. Sub-Workflow 11: Pelaporan & Governance

Pengguna Utama: Admin Manager

Langkah

  1. Admin buka Dashboard Governance (governance.html):
    • 4 kad KPI: Pesakit Aktif, Kadar Kepatuhan, KYC Diluluskan, Stok Rendah
    • Pembahagian Outcome Pesakit (Dalam Rawatan / OTW / Berhenti / Meninggal)
    • Pengagihan Pakej (% per pakej)
    • Ring Kehadiran Sesi (kadar 30 hari)
    • Funnel KOB
    • Kesihatan Inventori
  2. Keupayaan penapis: Mengikut penyakit, umur, jantina, negeri, lokasi, pakej (penapis penuh Fasa 2).
  3. Drill-down ke Laporan Pakej (pakej-laporan.html): Ringkasan semua pakej dengan bilangan pesakit. Klik baris → pakej-report.html?id=X untuk aktiviti terperinci.
  4. Audit Log (audit.html): Semua tindakan sensitif dilog. Boleh ditapis ikut actor, jenis aksi, tarikh. 500 entry terkini; eksport CSV untuk pematuhan.

Titik Keputusan & Pengendalian Ralat

  • Julat tarikh laporan → default 30 hari; julat custom tersedia
  • Akses drill-down → admin lihat semua; manager lihat operasi; coach lihat pesakit sendiri
  • Set data kosong → empty state dengan prompt
  • Query besar → pagination + indicator loading
Ringkasan: Dashboard governance beri KPI real-time kepada pengurusan. Audit log simpan semua tindakan untuk pematuhan. Laporan drill-down dari klinik → per-pakej → per-pesakit.

14. Sub-Workflow 12: Self-Help Library

Pengguna Utama: Admin Pesakit Coach (lihat)

Langkah

  1. Admin upload kandungan dalam library.html: Tajuk, deskripsi, jenis (video/artikel/PDF/audio/link), URL, kategori, ikon. Toggle Akses Pakej: Public ATAU ID pakej tertentu.
  2. Pengagihan kandungan:
    • Item public → kelihatan kepada semua pesakit
    • Item terhad → hanya pesakit dengan active_package_id yang padan
  3. Pesakit browse library: Auto-tapis ikut active_package_id. Kategori: Berjemur, Zikir Bersanad, Terapi Bumi, Pernafasan Fitrah, Herba Thoharah, dll.
  4. Coach/Doktor browse semua kandungan untuk rujukan / kongsi.
  5. Dikait dalam Detail Pakej: pakej-detail.html tunjuk "Kandungan Pakej" — item library yang ditapis padan pakej.

Titik Keputusan & Pengendalian Ralat

  • Jenis kandungan = video → pemain tertanam; link → buka luaran tab baru
  • Pakej dinaik taraf → pesakit dapat akses kandungan terhad pakej baharu
  • URL rosak → alert admin; kandungan disembunyi dari paparan pesakit
  • Pesakit tanpa pakej aktif → kandungan public sahaja
Ringkasan: Library adalah pangkalan pengetahuan bantuan kendiri. Kandungan boleh public atau terhad-pakej. Akses pesakit auto-tapis ikut pakej aktif; kandungan library juga muncul di halaman detail pakej.

15. Modul Rentas: Pembayaran & Invois

Pengguna Utama: Admin Pesakit

Langkah

  1. Pembayaran dipicu dari: Booking KOB, Pembelian Pakej, Minggu Extension, Produk Add-on.
  2. Kaedah pembayaran Integrasi Fasa 3: FPX, Kad, Transfer, GHL.
  3. Admin urus pembayaran dalam payment-admin.html: Tapis ikut status/kaedah/tempoh, entry manual untuk offline, tanda pending → completed.
  4. Penjanaan invois: Butang "Jana Invois" → invois A4 boleh dicetak. Nombor invois stabil INV-YYYYMM-{last6id}. Stylesheet cetak sembunyikan nav.
  5. Masa depan: Auto-hantar invois via WhatsApp + email Fasa 3.
Ringkasan: Modul pembayaran adalah lapisan kewangan. Semua transaksi dijejak ke psy_payments; invois boleh dicetak atas permintaan. Refund tidak disokong sekarang.

16. Modul Rentas: Audit Log

Pengguna Utama: Admin

Langkah

  1. Setiap tindakan sensitif tulis ke psy_audit_log: actor_id, actor_name, actor_role, action, target, meta (JSONB).
  2. Jenis tindakan termasuk:
    • kyc.approved, kyc.rejected
    • package.created, package.updated, package.activated, package.deactivated
    • plan.week_hadir, plan.week_updated, plan.extension_created
    • inventory.auto_deducted, inventory.manual_adjusted
    • payment.created, payment.refunded
    • staff.added, staff.removed
    • issue.reported, issue.closed
  3. Admin semak dalam audit.html: Tapis ikut aksi, peranan, tarikh, actor. 500 entry terkini. Eksport CSV.
